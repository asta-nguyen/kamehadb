# DBX database agents: lessons for the Go provider core

Date: 2026-10-19. Scope: database driver architecture, not AI agents or ACP.

Reviewed DBX source pinned to commit `d9c464d7d5c41c7c2993d7ea19a3ffcfb2353292` (the previously selected v0.6.42 snapshot). Sources were read, not built or executed. Recommendations below are architectural inferences, not proposed additions to the current implementation plan.

## What DBX actually does

**Its topology is mixed.** The database manifest distinguishes `native`, `file`, `agent`, and `external` runtime modes. PostgreSQL and MySQL are marked native; SQLite is file based. Driver modules also expose native PostgreSQL, MySQL, MongoDB, and Redis implementations alongside agent support and a feature gated DuckDB sidecar. “Every database runs in a child process” would be inaccurate. [Manifest](https://github.com/t8y2/dbx/blob/d9c464d7d5c41c7c2993d7ea19a3ffcfb2353292/crates/dbx-core/assets/database-drivers.manifest.json), [runtime model](https://github.com/t8y2/dbx/blob/d9c464d7d5c41c7c2993d7ea19a3ffcfb2353292/crates/dbx-types/src/database_manifest.rs), [driver modules](https://github.com/t8y2/dbx/blob/d9c464d7d5c41c7c2993d7ea19a3ffcfb2353292/crates/dbx-drivers/src/db/mod.rs).

**Database agents use actual JSON-RPC 2.0 over stdio.** Requests contain `jsonrpc: "2.0"`, `id`, `method`, and `params`; framing is newline delimited JSON, not Content-Length headers. Startup first waits for a separate `{"ready":true}` message. Responses are matched to pending requests by ID. The handshake exposes `protocolVersion`, `agentProtocolVersion`, and capabilities. Shared runtimes require protocol v2 and `multi_session`; the legacy client's handshake is optional and even other handshake failures can fall back to legacy behavior. Do not copy that permissive compatibility policy into a new protocol without an existing compatibility requirement. [Transport and handshake implementation](https://github.com/t8y2/dbx/blob/d9c464d7d5c41c7c2993d7ea19a3ffcfb2353292/crates/dbx-driver-agent/src/agent_driver.rs#L42-L108), [framing](https://github.com/t8y2/dbx/blob/d9c464d7d5c41c7c2993d7ea19a3ffcfb2353292/crates/dbx-driver-agent/src/agent_driver.rs#L134-L148), [legacy handshake](https://github.com/t8y2/dbx/blob/d9c464d7d5c41c7c2993d7ea19a3ffcfb2353292/crates/dbx-driver-agent/src/agent_driver.rs#L3147-L3167).

**Process ownership differs from connection ownership.** Protocol v2 multiplexes logical database sessions into one runtime. `agentSessionId` identifies the connection; existing `sessionId` values identify cursors. Same-session requests serialize; different sessions can progress concurrently. Cancellation and close target one session. EOF fails all outstanding requests, and the failed runtime leaves reuse before recreation on demand. Structured errors distinguish keeping a session, quarantining it, and replacing a runtime; they also distinguish an operation that never started from an unknown outcome. A retry hint does not authorize replaying SQL. [Protocol v2 lifecycle and recovery](https://github.com/t8y2/dbx/blob/d9c464d7d5c41c7c2993d7ea19a3ffcfb2353292/agents/docs/agent-protocol-v2.md).

**Static declarations and runtime abilities are different concerns.** The manifest includes driver identity, runtime mode, profiles, managed packages, ports, feature capabilities, and product traits. Runtime handshake capabilities describe what an installed agent implements. Package presence alone does not imply agent transport: catalog tests explicitly cover DuckDB and SQLite SSH worker packages without classifying those engines as agent runtimes. [Manifest](https://github.com/t8y2/dbx/blob/d9c464d7d5c41c7c2993d7ea19a3ffcfb2353292/crates/dbx-core/assets/database-drivers.manifest.json), [catalog](https://github.com/t8y2/dbx/blob/d9c464d7d5c41c7c2993d7ea19a3ffcfb2353292/crates/dbx-driver-agent/src/agent_catalog.rs).

**Optional drivers include both native executables and JDBC JARs.** Java agents use a managed JRE, while native agents do not require one. Drivers have independent artifact versions. JDBC packaging distinguishes redistributable bundled drivers from externally supplied drivers, with a release registry flag for the latter. This is a distribution and compatibility mechanism, not evidence that JDBC or subprocesses should replace mature Go drivers. The Java authoring guide's broad “every agent is a JVM process” wording is narrower and older than the native implementations documented in the agents README. [Agents README](https://github.com/t8y2/dbx/blob/d9c464d7d5c41c7c2993d7ea19a3ffcfb2353292/agents/README.md), [JDBC packaging guidance](https://github.com/t8y2/dbx/blob/d9c464d7d5c41c7c2993d7ea19a3ffcfb2353292/agents/docs/agent-authoring.md#driver-packaging).

## Apply selectively to KamehaDB

1. **Keep the provider core independent of transport.** Connection lookup, lifecycle, operation contracts, and engine capabilities should work with today's in-process Go adapters. A future process adapter can satisfy the same contracts when a concrete driver requires isolation, JDBC, native libraries, or separate installation. No migration of all current drivers follows from DBX's design.
2. **Avoid concrete adapter types at the reusable core boundary.** Returning `*mongo.Adapter` or `*redis.Adapter` ties callers to current implementations. Where the core needs those operations, narrow consumer-needed interfaces preserve a future transport seam without inventing a universal SQL-shaped API for MongoDB and Redis. Extract only methods actual callers need.
3. **Give close operations explicit scope.** A connection manager's `Close` should release the connection/session it owns. A shared runtime owner should terminate the process only when appropriate. This matters if multiple connections later share one worker: closing a tab must not kill sibling connections, and a process crash must invalidate every affected session.
4. **Keep capabilities truthful and small.** Reuse existing engine metadata and constants; add only capabilities needed to route current operations. If downloadable providers arrive, separately track declared features, installed availability, and negotiated runtime support. A large copied DBX manifest is unnecessary now.
5. **Define recovery before adding process transport.** That future implementation needs bounded startup, version negotiation, request IDs, cancellation, session/cursor cleanup, EOF handling, and tests for concurrent sessions and unknown write outcomes. Preserve `context.Context` and typed errors through current contracts so transport does not force a second lifecycle later. Never retry an uncertain write automatically.

Skipped: DBX execution, performance measurements, database-count comparisons, AI/CLI behavior, and changes to KamehaDB source or its implementation plan. Risk: DBX mixes legacy compatibility paths and newer shared runtimes; copying only its simple process diagram would omit important lifecycle behavior.
