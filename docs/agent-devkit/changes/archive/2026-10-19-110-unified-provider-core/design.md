# Unified database provider core

Issue: [#110](https://github.com/asta-nguyen/kamehadb/issues/110)

## Goal

Give every supported database one Go entry point for provider selection and connection ownership. KamehaDB must use the same reusable core that an external Go consumer can import, preparing an all-in-one provider library without publishing a release in this change.

## Scope

- Add public packages under `dbcore/` in the existing Go module. Do not create a nested module, separate repository, npm package, release workflow, or new dependency.
- Reuse and relocate existing adapter implementations and their tests; do not rewrite database operations. Support the existing ten engine kinds, including the shared MySQL/MariaDB implementation.
- Centralize GUI SQL/MongoDB/Redis provider construction, caching, invalidation and close ownership. Preserve the existing bound service families and frontend behavior.
- Move reusable contracts/helpers from `internal/engines/` to `dbcore/engines/`, splitting live kinds from app-only legacy/MCP metadata, SQL implementations to `dbcore/providers/<engine>/`, and MongoDB/Redis implementations to `dbcore/providers/mongo/` and `dbcore/providers/redis/`. Extract their operation interfaces and request/result types into driver-free `dbcore/mongo/` and `dbcore/redis/` contract packages; do not duplicate type definitions.
- Move the DuckDB helper client/protocol/installer to `dbcore/duckdriver/`; keep its native implementation at `dbcore/providers/duckdb/embedded/`, imported by the existing helper executable only. Keep mongosh installation/PTY integration in the app, outside the provider package.
- Move `internal/sqlsafety/` and its tests to `dbcore/sqlsafety/`; update SQL export, GUI and MCP screening imports together, retaining one screening implementation and its existing guarantees.
- Keep credential storage, profile persistence, GUI request ownership, metadata/result caching, history, Wails, terminal jobs, schema workflows, AI orchestration and MCP authorization in the application.
- Preserve all existing query/result limits, SQL optional capabilities, cancellation behavior, TLS settings, no-replay rules, read-only constructors and DuckDB isolation.

This is package preparation and app migration. Publishing/versioning the library independently, changing query languages, unifying result formats, redesigning the UI, adding database engines and finishing the separate performance change are outside scope. Do not add a generic process runner, JDBC/JRE support, shared worker runtime, downloadable-provider marketplace, a large driver manifest, or a new JSON-RPC protocol in this change.

### One entry point, engine-specific operations

`dbcore.Registry` selects a registered provider using the existing connection kind. Its `Open(ctx, config)` creates an uncached provider owned by the caller. `dbcore.Manager` uses the same registry with an injected profile loader and exposes `Get(ctx, connectionID, acceptConfig)`, `Invalidate(connectionID)` and `Close()` for app-managed reuse.

`acceptConfig` is a nullable `ConfigCheck` callback with shape func(Config) error. The app facade supplies its family check; generic library callers may pass nil. Manager.Get evaluates the caller's check on the exact immutable config selected for that entry before resolving/starting its factory, and on an entry's stored config before returning a cached provider or admitting a waiter. Rejection returns that caller's error without constructing a provider for that request, poisoning the entry or cancelling other accepted waiters. With only rejected callers no factory is invoked. A family check performs no I/O and cannot mutate the config. A new entry reloads config after invalidation. This uses the manager's existing load and avoids a separate app preflight read whose Kind could become stale between reads. Registry.Open already receives an explicit config; the app applies its same family check to that config before Open for typed uncached probes.

A managed entry owns the context passed to its factory, derived from the manager lifetime, not the first Get caller. Each caller's context only controls its wait. One cancelled waiter cannot cancel construction needed by another waiter. If the last waiter abandons unfinished construction, retire that entry and cancel its entry context; any late result is closed and cannot be cached. Invalidate and manager Close also retire/cancel the entry. A later get after retirement starts a fresh entry and reloads the profile. Registry.Open passes its caller context directly because it has no shared entry. Factories check context before/after existing non-context constructors; when a native constructor cannot interrupt, its late result is closed rather than published.

The manager owns exactly one cached provider per connection ID within that manager. Different manager instances never share sessions. Its common lifecycle applies to SQL, MongoDB and Redis. Provider constructors retain native driver pools and request-specific behavior; the manager does not replace those pools.

The root package imports contracts, not concrete drivers. Consumers may register individual providers. `dbcore/providers/all.New(options)` explicitly assembles all ten kinds into a registry without opening connections. Factory registration is instance-local, rejects duplicate kinds and does not rely on global `init()` registration.

### Preserve native capabilities

The common `Provider` contract contains `TestConnection(context.Context)` returning the existing test-result shape, and `Close() error`. It does not contain a generic untyped execute method.

SQL providers expose `SQL() engines.SQLAdapter`. MongoDB and Redis providers expose `Mongo() mongo.Operations` and `Redis() redis.Operations`, where the return types are interfaces in the driver-free contract packages. No core accessor or GUI lookup returns a concrete driver adapter. Thin lifecycle holders adapt existing constructors and MongoDB's context-taking close; they do not reimplement query behavior. Optional SQL capabilities are asserted on the original SQL adapter, preserving export, metadata-aware preview, statistics and bounded reads.

The required Mongo contract includes ListDatabases, ListCollections, FindDocuments, Aggregate, RunCommand, UpdateDocument, DeleteDocument, GetCollectionStats and the CountDocuments operation completed by footprint Task 10. The required Redis contracts include GetTTL, GetStats and ForRequest, whose request-scoped capability includes ScanKeys, GetKey, RunCommand and the value-page operation completed by footprint Task 11. Include cursor-release/lease cleanup operations introduced by footprint Task 11 and consumed by frontend Task 12 at their actual ownership scope: cursor release is not interchangeable with closing a request-local client. The exact post-footprint method signatures and placement are established by Task 1's prerequisite source inventory, not guessed from unfinished code. Copy that verified context, argument and result shape, replacing only concrete adapter returns with contract interfaces. ForRequest still supplies request-local cleanup. Borrowed operation interfaces do not expose provider Close. MCP's existing narrow bounded-read interfaces stay separate.

Capabilities are determined by implemented operation/accessor interfaces, not by a declared database kind alone. Unsupported optional operations remain unavailable; do not invent manifest entries or claim availability merely because a provider package is registered.

Each Mongo/Redis provider factory owns the one conversion from core Config/ConnProfile to its native driver config. Mongo maps the already-resolved ConnectionString and Database. Redis maps Host, Port and Password, uses logical database zero for empty/invalid/negative database strings as the current app does, and accepts a valid nonnegative parsed database index. Driver defaults and connection errors remain unchanged. Managed opens and fresh test probes reuse this same mapping; remove the copies in API services and connection probing. The app retains profile lookup/decryption and wrong-family error translation, not native config construction. Preserve the exact GUI wrong-kind messages: "Connection %s is not a mongodb connection" and "This endpoint is for redis connections only", and reject those mismatches through the app-supplied ConfigCheck before factory dispatch. SQL lookup preserves "Use /mongo endpoint for MongoDB connections", "TigerBeetle is not a SQL database" and "Password not saved. Open connection settings and save with password." through app checks/error translation; core capability errors remain separate.

The root package owns typed helpers `dbcore.SQL(p)`, `dbcore.Mongo(p)` and `dbcore.Redis(p)`. Each returns its operation interface plus an error; absent capability, including a nil provider/capability, returns the shared `ErrCapabilityUnsupported`. Helpers perform the accessor assertion in one place; consumers do not repeat it. An unregistered kind instead returns `ErrProviderNotRegistered`. Optional SQL operations retain their existing small-interface assertions on the SQL capability.

Calling a SQL service with a MongoDB/Redis profile fails before a SQL operation runs. Capability mismatch and unregistered kind are distinguishable library errors. The application translates library errors to its existing user-facing error conventions. Existing SQL unsupported-adapter behavior, where still required, stays in an app compatibility adapter rather than making the library pretend an unknown engine is supported.

### Transport and runtime ownership

The provider contract is independent of transport: the existing Go drivers run in-process, while DuckDB remains backed by its existing private stdio helper. The manager and callers operate through the same typed contracts without branching on process/native mode. A future JDBC or process provider can implement these contracts, but no such provider or generic transport framework is implemented here. Preserve DuckDB's current protocol; DBX's JSON-RPC 2.0 is research context, not a protocol-migration requirement.

`Provider.Close()` releases the connection/session owned by that provider. `Manager.Close()` releases every provider owned by that manager; neither method means terminate an arbitrary shared runtime. DuckDB currently owns one helper per provider, so its close still terminates that owned child. If a future provider shares a worker, that provider's separate runtime owner must preserve sibling sessions and retire every affected session on worker failure. This change adds no shared-worker implementation or reference-counting framework.

Keep operation contexts, typed lifecycle errors and existing backend cancellation intact across both current execution modes. A process EOF or timeout after dispatch can leave the write outcome unknown: report that uncertainty using the existing behavior and never automatically reconnect-and-replay. Static engine metadata and future negotiated runtime capabilities must remain distinct; only current implemented capabilities are exposed now.

### App wiring and ownership

The application supplies its profile loader and decrypted config to the core; the library never imports the application's metadata store. A small `internal/database/` integration package supplies SQL lookup and typed MongoDB/Redis lookup to existing services and builds app-specific provider options. The old SQL registry and the MongoDB/Redis service-local adapter maps disappear after their callers migrate.

Profile update/delete and file backup/restore continue through the existing invalidation entry point: cancel affected GUI requests/exports, retire and close the managed provider, clear app caches, and invalidate MCP separately. Shutdown stops request-producing work and cancels owned jobs before closing the GUI manager and metadata store. The manager's final `Close()` is idempotent and rejects subsequent gets. Preserve current probe selection: TestConnection for unsaved dialog input uses uncached Open and closes the provider; CheckConnectionHealth for a saved SQL profile uses Manager.Get and tests the cached SQL adapter; saved MongoDB/Redis health probes use a fresh uncached provider and close it, preserving their current semantics. Background DuckDB health uses Manager.Get plus BackgroundHealth without initializing the helper. An explicit user-requested DuckDB test may initialize it. Tests must count factory calls and closes for each path rather than treating every probe as uncached.

By the end of Task 4, SQL service, schema capture, AI SQL context, MongoDB operations and Redis operations all obtain GUI providers through the same manager. Construction, cache reuse, invalidation and shutdown are checked across SQL service/schema/AI in the same container; the unused indexer retains only its updated lookup signature and no new production wiring; the old registry is not a second production cache. Mongo shell/terminal functionality remains app-owned and is not closed as a side effect of closing a borrowed provider capability. Services must not independently close manager-owned adapters.

MCP continues to own its separate manager, credential bundles, allowlist, read-only adapters, database scopes, timeouts and concurrency limits. It reuses relocated provider constructors and bounded-read capabilities, not GUI sessions. Provisioning continues to use its existing explicit privileged flow.

### Package boundary and runtime configuration

The entire `dbcore/` tree must have no imports of `github.com/asta-nguyen/kamehadb/internal/...` or Wails. Connection config, the ten live kinds/defaults and SQL contracts have one Go definition under `dbcore/engines/`; `dbcore.Config` aliases the connection config for the root API. Do not move kinds.go wholesale: keep KindQdrant, KindTigerBeetle, the persisted legacy-inclusive AllKinds/CHECK ordering, legacy display ports and MCPServerKinds/MCPSupportedKinds plus their policy helpers in app-owned `internal/engines/kinds.go`. Its references to the ten live constants use the public definitions. Build the app DefaultPorts map by copying the public live map and adding only the legacy entries; do not repeat the ten live port values or mutate the public map. Preserve app IsValidKind/migration semantics for old profiles while public AllKinds/IsValidKind describe exactly ten supported providers. App MCP/store callers continue using app policy metadata; public providers must not import it. Existing JSON names, nullability and payload behavior stay unchanged. Keep Go package names engines/mongo/redis so existing generated namespaces are expected to remain unchanged; regenerate and compare bindings to verify that expectation. No frontend namespace rename is intended.

DuckDB provider options require an explicit runtime directory and accept an optional diagnostic callback. App wiring supplies `store.DataDir()` and its existing logger. Creating the registry or provider must not create directories, download binaries, start helpers or open a database. Missing runtime configuration fails on explicit DuckDB initialization. Preserve the current trusted helper installer, release version/checksum linkage, development override, handshake, crash behavior, spill cleanup and non-initializing background health capability. Do not turn DuckDB back into an embedded desktop dependency.

The existing Go module remains the distribution unit. Public importability is proven using a temporary consumer module with a local `replace`; this does not promise independent package versioning, a small module download, or universal driver/platform availability. An all-in-one import includes all driver dependencies; a selective import avoids unrelated driver linkage.

## Edge cases

1. Unknown kind, duplicate registration, missing profile, missing required password and wrong capability: return a distinguishable error before database work; preserve empty-versus-unsaved password semantics and current profile validation.
2. Concurrent first gets for the same ID: share an entry-owned factory context, publish one provider and close any losing construction exactly once. Different IDs may construct independently; no network construction holds a global manager lock.
3. Invalidate/close during construction: retire the entry before returning; a late constructor cannot repopulate the cache and its provider is closed. A new get after invalidate resolves the latest config; a get after manager close fails.
4. Cancelled get: do not publish a provider constructed for an abandoned/retired entry. A cancelled waiter must not cancel a factory or provider needed by another caller; the final departing waiter retires unfinished construction and prevents late publication. Cancelled native operations keep their existing request-specific behavior.
5. Constructor failure: no failed entry is retained as a successful provider; an explicit later get may retry construction. Never automatically replay a database operation after a connection error or helper crash.
6. Profile mutation/shutdown: cancel owned work before adapter close. Invalidating one ID or closing a request-specific Redis client must not close another connection or another request's shared client.
7. MCP and GUI address the same profile ID: credentials, sessions and teardown remain isolated. Missing managed credentials cannot fall back to GUI credentials.
8. Close failure: remove the provider from ownership even if teardown reports an error; aggregate close errors without logging config/password/URI secrets. Callers route diagnostics through existing app logging.
9. DuckDB: repeated background health checks create no helper, database or runtime directories; explicit runtime failures retain existing trusted-download and no-replay behavior.
10. Alternate implementations: interface-based Mongo/Redis fakes work through the same lookup without concrete adapter imports. Closing one provider session leaves a sibling session alive; the existing DuckDB-owned child still stops on its provider close. EOF after dispatch fails pending work without automatic replay or a false success result.
