Verification: [x] Provider settings, chat requests, schema context, embedding indexing, and chat persistence were checked against current desktop and sidecar source.

## Provider settings

### Business rules

- API Settings exposes Ollama local, Ollama cloud, OpenAI, 9router, DeepSeek, and Gemini provider choices.
- Settings include provider/model and provider-specific connection or credential values. The UI supports editing, saving, discarding, and choosing the active provider.
- Provider settings are persisted in metadata SQLite. The inspected sources do not establish OS Keychain encryption for these AI settings.

### Flow

1. The desktop loads settings through the AI settings hook.
2. The user edits a provider configuration and saves through the sidecar API.
3. The sidecar validates and stores settings in metadata SQLite.
4. The desktop invalidates the AI-settings query and uses the active configuration for chat and indexing.

### State changes

- Provider configuration is persisted in metadata SQLite.
- The active provider selection is used by subsequent chat and embedding requests.

### Side effects

- Saving settings changes which configured provider the sidecar calls for future chat and embedding operations.

### Authorization & constraints

- Provider-specific API keys are required where the provider configuration requires them; local Ollama can be used without a hosted provider key.
- Settings access uses the authenticated local sidecar API.

### Error paths

- Invalid provider settings are rejected by sidecar validation.
- Invalid credentials, unreachable provider URLs, or unsupported models surface when the sidecar attempts the provider operation.

## Schema-aware chat and chat history

### Business rules

- The chat panel sends user messages, active connection context, and relevant schema context to the sidecar.
- SQL chat can produce a query, pass it through the shared query-safety check, execute it, and send up to 50 result rows back to the provider for a final response.
- MongoDB chat receives Mongo schema context. Redis and TigerBeetle use engine-specific system prompts in the inspected route.
- User and assistant messages are persisted in local chat history, scoped to connection and Mongo database where applicable.

### Flow

1. The desktop opens chat for a connection and sends messages to the sidecar chat route.
2. The sidecar builds schema context, selects the configured provider, and streams provider output back to the frontend.
3. For SQL responses that contain a query, the sidecar checks query safety and may execute the query through the SQL adapter.
4. The sidecar persists chat messages and the desktop exposes recent history and clear-history actions.

### State changes

- Chat messages and chat history are stored in metadata SQLite.
- Clearing history can target the connection and, for MongoDB, the selected database.
- Streaming and cancel state are transient in the desktop.

### Side effects

- The selected provider receives the prompt and the schema context assembled for that turn. For remote providers, the configured remote endpoint receives that request payload.
- SQL chat may issue a database read and includes a bounded result sample in a follow-up provider request.
- On sidecar startup, the configured indexing path can build schema embeddings and persist vectors in metadata SQLite.

### Authorization & constraints

- All provider calls use the saved active provider settings.
- SQL generated by chat is subject to the shared safety heuristic before execution.
- Inference from the inspected request construction: schema descriptions and user prompts are sent to the configured provider. Source does not establish provider-side retention or processing guarantees.

### Error paths

- Missing provider credentials, provider network errors, streaming failures, invalid generated SQL, and database errors can terminate or annotate the chat response.
- Frontend cancellation aborts the current chat request; a canceled request is not itself proof of a database failure.
- Embedding API failures fall back to the local embedding implementation in the provider module.
